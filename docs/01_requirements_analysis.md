# 01 需求分析

> 本文档回答三个问题：**给谁做、解决什么问题、做到什么程度算成功**。
> 所有"成功标准"都在 `config/dataset.py` 的 `EVALUATION.acceptance` 里有对应代码实现，
> 由 `python -m src.evaluate` 自动判定，避免"标准写在文档里、跑的时候没有"。

---

## 1. 背景与问题定义

可穿戴设备（手环、手表、手机）已经能记录步数、心率、睡眠时长等数据，但这些数字通常以
"昨天睡了 6 小时 42 分"的形式事后呈现：用户看完只知道**结果**，不知道**这个结果和什么有关**，
也不知道**今晚大概会怎样**。睡眠又是一个典型的"行为影响结果、结果反过来影响第二天行为"的场景，
用户真正需要的是**就寝前的预期管理**。

因此本项目把任务定义为：

> **在用户今晚就寝之前，根据今天白天的活动量与用户的历史记录，预测今晚的睡眠时长，
> 并用用户能看懂的方式说明这个预测的不确定性和主要影响因素。**

关键限定（决定了整个系统的技术边界）：

| 维度 | 定义 |
|---|---|
| 预测时点 | 今晚就寝前（入睡之前） |
| 可用信息 | 今天白天的活动（步数、中高强度活动、久坐）、历史记录（既往睡眠与活动）；"计划就寝时刻"**取决于数据集**——合成数据里有，真实 Fitbit 日表没有（见 `docs/03_data_source.md` 第 3.1.2 节） |
| 禁止使用 | 今晚的实际睡眠数据（含卧床时间、睡眠效率）、未来的任何信息 |
| 预测目标 | 当晚睡眠时长（分钟，回归任务） |
| 输出形式 | 点预测 + 80% 预测区间 + 可信度标签 + 影响因素说明 |

"禁止使用"这一条不是形式主义：如果允许使用当晚的卧床时间或睡眠效率，模型会得到
看起来非常漂亮的指标，但产品上线后根本拿不到这些输入——这就是典型的数据泄漏。

## 2. 目标用户与使用场景

### 2.1 用户画像

| 画像 | 特征 | 对系统的主要期待 |
|---|---|---|
| **A. 想改善作息的学生 / 上班族（主要用户）** | 20–35 岁，有手环或手机计步，作息不规律，周末补觉 | 想知道"今晚大概能睡多久""我做了什么让它变短" |
| **B. 关注健康的普通用户** | 30–50 岁，关注步数与睡眠，但没有医学背景 | 需要结论清晰、不要术语、不要制造焦虑 |
| **C. 课程评委 / 同学（次要用户）** | 需要检查方法是否严谨、是否可复现 | 需要模型对比表、错误分析、AI 使用说明 |

### 2.2 使用场景（主场景）

> **场景**：晚上 22:30，用户准备洗漱。今天加班，步数只有 3,000，久坐 9 小时，
> 预计 00:30 才能睡。他打开原型，填入今天的数据，得到"预计睡 6 小时 10 分，
> 可能在 5 小时 20 分 ~ 7 小时之间（把握：中等）"，并看到"就寝时刻比你的平均状态晚 1 小时，
> 使预测减少约 25 分钟"。
>
> **注（换用真实数据后）**：这是需求阶段写的理想场景。真实数据 `fitbit_bellabeat` 里
> **没有"就寝时刻"字段**，所以实际界面不会出现最后那句归因（界面已做到"没有该字段就不显示该输入"）；
> 而"点预测 + 区间 + 把握：中等"这三个要素已由真实数据验证过，见 `reports/metrics.md` 与 `reports/error_analysis.md`。

这个场景决定了三条设计原则：

1. **输入必须少而容易获得**：睡前没人愿意填 20 个字段，核心字段 ≤ 6 个；
2. **结论必须先给**：先"6 小时 10 分"，再解释为什么；
3. **不能制造虚假精确**：必须同时给出区间和可信度，否则用户会把 6.17 小时当成事实。

### 2.3 用户 ≠ 被预测对象

本项目的模型是在**群体数据**上训练的，用于推断**个体**的夜晚——这是"个性化"与"泛化"的张力。
明确写下这条，是为了避免"给某个用户推荐一个通用结论"，也是第 6 节中把
"与个人历史均值对比"作为固定解释模块的原因。

## 3. 任务分析

### 3.1 用户任务 vs 系统任务

| 用户想做的事 | 系统的任务 | 对应模块 |
|---|---|---|
| 快速描述今天的情况 | 提供最小输入表单 + 默认值 + 历史自动载入 | `app/app.py` 第 1 页 |
| 知道今晚大概睡多久 | 点预测 | `src/predict.py` |
| 知道这个数字有多可靠 | 分位数区间 + 可信度标签 | `src/train.py`（分位数模型）、`src/metrics.py` |
| 知道"为什么" | 反事实逐项归因 + 自然语言文案 | `src/explain.py` |
| 知道这个系统值不值得信 | 模型卡、典型误差、数据来源、局限性说明 | `models/model_card.json`、`reports/*.md` |
| 知道它**不能**做什么 | 免责声明 + 相关≠因果的反复提示 | `app/app.py` 全局 |

### 3.2 任务分解（交互层）

```
[1] 输入今天的情况  ->  [2] 查看预测结果  ->  [3] 看解释与提醒
        ↑                                             │
        └──────────── 修改输入 / 重新开始 ←────────────┘
```

每一步只解决一个问题，不做"信息大杂烩"。第 2 步同时给出"结论 + 不确定性 + 与自己的对比"，
第 3 步才展开归因，避免首屏过载。

## 5. 非功能需求

| 类别 | 要求 | 具体做法 |
|---|---|---|
| **可信** | 指标必须来自未参与训练的测试集 | 测试集只在 `src/evaluate.py` 中使用一次；`src/train.py` 只读 train / val |
| **可解释** | 解释必须能被非专业用户读懂，且不夸大因果 | 反事实归因 + 中文模板文案 + 固定的三条 caveat |
| **不确定诚实** | 不允许只给一个点估计 | 分位数区间 + 可信度标签（较高/中等/较低）+ 典型误差（±X 小时） |
| **可用性** | 三步内完成一次预测，输入字段少、有默认值 | 单页表单、核心 4 项必填、其余折叠 |
| **隐私** | 不收集、不上传任何用户数据 | 原型在本地运行；演示用的是内置历史样本 |
| **可复现** | 固定随机种子，一次命令跑通 | `random_seed = 42`；README 第 1 节给出命令序列 |
| **可维护** | 业务代码不硬编码路径与列名 | 全部走 `src/config.py` |
| **健壮** | 缺少可选依赖（如 lightgbm、shap）不崩溃 | 可选依赖 try/except + 降级方案（反事实解释代替 SHAP） |

## 6. 信息架构与界面需求（HCI 重点）

### 6.1 每一步要回答用户的一个问题

| 页面 | 用户的问题 | 界面提供的答案 | 设计理由 |
|---|---|---|---|
| 1 输入 | "我要填什么？" | 3–4 个核心输入（步数、中高强度活动、久坐，**"计划就寝"仅当数据集含该字段时才出现**）+ 折叠的可选项 | 睡前场景下输入成本必须低；默认值取自历史，减少"必须填对"的压力；当前 Fitbit 日表没有就寝字段，界面就不显示该项（不做"填了也没用"的假控件） |
| 2 结果 | "今晚会怎样？有多准？" | 大字号结论 + 80% 区间 + 可信度徽标 + 与个人均值对比 + 典型误差 | 先结论后细节；不确定性用颜色和一句话表达，而不是只给数字 |
| 3 解释 | "为什么是这样？我能改什么？" | 影响最大的 3–5 项 + 每一项的分钟数 + 三条理解提醒 | 归因必须落到具体行为，同时防止用户把相关当成因果 |

| 4 | 输入（侧栏「预测对象」） | "现在预测的是谁？这套说法是说我的吗？" | 顶部二选一：**手环用户**（Fitbit 日表，无性别列）/ **睡眠健康人群**（横截面，**含性别输入**）；换人群＝换数据集＋换模型，结果页与解释页的参照对象随之一致 | 两条线的预测目标不同（"今晚睡多久" vs "这类人的睡眠时长"），参照值也不同（个人历史平均 vs 数据集里的**示例记录**）；界面**不把两套 MAE 并列比大小**（3.56 分钟 vs 41.9 分钟的差异来自数据生成方式，不是模型强弱） |

### 6.2 关键界面设计决策（与依据）

1. **先给区间还是先给点估计？** 先给点估计（大字），紧邻给区间。
   理由：用户的心理锚点是"今晚能睡多久"，直接给区间会让人无处着手；
   但区间必须与点估计同时出现，否则会强化"精确预测"的错觉。
2. **可信度用文字标签而不是数字**（较高/中等/较低）。
   理由：受访者普遍不理解"置信区间宽度 84 分钟"的含义，而"这次把握中等"可直接用于决策。
3. **固定显示"与你的平均相比"**。
   理由：群体模型对个体存在偏差，用个人基线做锚点，用户更容易判断预测是否离谱。
4. **所有解释都是"相对你的平均状态"**。
   理由：反事实解释需要参照值，用个人历史平均最贴近用户直觉，也避免"和别人比"的隐性评判。
5. **全局保留免责声明与"不是因果"提示**。
   理由：睡眠涉及健康，界面不得暗示诊断或治疗建议。
6. **诚实报告不确定性来源**：区间宽时明确说"这次输入与训练数据不太接近"，
   而不是含糊地用"可能有误差"带过。

7. **人群切换做成侧栏第一项，而不是新开一个页面**。
   理由：两条线共用"输入—结果—解释"三步，只有**数据说明书**（能填哪些字段、上下限、默认值、参照口径）不同；
   若新开页面，会出现两套并行维护的界面逻辑，且用户会拿两套指标直接比大小。
   控件由数据集说明书 + 模型卡渲染（`requires_feature` 前缀匹配），保证**界面上出现的每个输入都真的影响结果**。

### 6.3 无障碍与文案要求

- 中文文案，避免"特征""分位数"等术语直接暴露给用户（内部归因说明除外）；
- 数字统一为"X 小时 YY 分"，不用 `6.17` 这类小数小时；
- 颜色不作为唯一信息载体（可信度既有颜色也有文字）；
- 关键说明使用短句 + 列表，单段不超过 3 行。

## 7. 成功标准

### 7.1 机器可验证（由 `python -m src.evaluate` 自动判定并在 `reports/metrics.md` 打勾）

| 指标 | 标准 | 依据 |
|---|---|---|
| 测试集 MAE | ≤ 0.75 小时（45 分钟） | 低于"用均值预测"的误差，且与文献中"日级睡眠时长预测"的可达精度同量级 |
| 相对均值基线提升 | ≥ 15% | 证明模型确实学到了信息，而不只是会输出平均值 |
| 80% 区间实际覆盖率 | 落在 70% ~ 90% | 低于 70% = 区间过窄（误导用户过度自信）；高于 90% = 过宽（没有信息量） |
| 划分泄漏自检 | 用户与日期不跨集合重叠 | 指标可信的前提 |

当前（**真实数据 `fitbit_bellabeat`**，2026-10-04 重跑）结果：

| 指标 | 实测 | 判定 |
|---|---|---|
| 测试集 MAE | **41.9 分钟（0.70 小时）** | ✅ 达标（≤ 45 分钟） |
| 相对均值基线提升 | **20.8%**（基线 MAE 52.8 分钟） | ✅ 达标（≥ 15%） |
| 80% 区间实际覆盖率 | **86.7%**（测试集）/ 80.0%（验证集） | ✅ 达标（70%–90%） |
| 划分泄漏自检 | 用户与日期均不跨集合重叠 | ✅ 达标 |

**必须一起写进报告的两句话：**

1. 指标比合成数据差很多（MAE 29.8 → 41.9 分钟）。这不是代码退化，而是**数据变难了**：
   真实数据的目标标准差是 100.8 分钟（合成数据 56.1 分钟），
   "直接用训练集均值预测"的 MAE 就有 52.8 分钟。真实数据上的这个成绩是有信息量的。
2. 75 条测试样本只来自 **4 名用户**（按用户分组切分的必然结果），
   分用户 MAE 从 29.8 到 54.0 分钟。因此 **MAE 必须写成"约 42 分钟（4 名测试用户）"**，
   不能当作对人群的精确结论——细节见 `reports/error_analysis_notes.md` 第 0 节。

### 7.2 人可验证（用户测试，见 `user_test/`）

| 维度 | 测量方式 | 通过线 |
|---|---|---|
| 可理解性 | 看完结果页后，用自己的话说出"今晚大概睡多久、有多准" | ≥ 4/5 人能正确复述 |
| 可操作性 | 说出"哪个因素影响最大" | ≥ 3/5 人能指出主要因素 |
| 信任校准 | 判断"这个预测是否绝对可靠" | ≥ 4/5 人回答"不是绝对的" |
| 效率 | 从打开页面到得到结论的时间 | 中位数 ≤ 1 分钟 |
| 情绪影响 | 是否感到被评判或焦虑 | 无人报告明显的焦虑感 |

> **人数口径**：本表按 5 人写。作业第 5 条要求"至少 3 名同学"，若最终只收到 3 人，
> 按同一比例换算：`≥ 4/5` → **3 人全中**，`≥ 3/5` → **≥ 2 人**，其余（中位数 ≤ 1 分钟、无人焦虑）不变；
> 换算表与实际分母的写法见 `user_test/tasks.md` 第 4 节、`user_test/summary.md` 第 1 节。

"信任校准"是本项目特有的一条：真实数据上模型误差约 42 分钟、80% 区间宽达 2.7 小时，
如果用户把它当成确定结论，比"完全不信"更危险。

## 8. 边界：本项目不做的事

1. **不做医疗诊断、不做睡眠障碍筛查**（`sleep_disorder` 字段只作为切片分析维度，不用于个体判断）；
2. **不做治疗性建议**（不输出"你应该服用…"），只描述"模型显示的相关关系"；
3. **不做实时监测与推送**（原型是"按需查询"的一次性交互）；
4. **不承诺个体精度**：所有指标都是群体平均精度，个体可能长期偏离；
5. **不做账号与数据上传**：输入仅存在于当前会话。

## 9. 假设、风险与应对

| 风险 | 说明 | 应对措施（本项目已实现或已记录） |
|---|---|---|
| 数据泄漏导致指标虚高 | 睡眠类数据最容易"用结果预测结果" | 明确预测时点；滞后/滚动特征一律 `shift(1)`；同夜卧床时间与睡眠效率进黑名单 |
| 样本量小、用户少 | Fitbit 公开数据仅 30 名用户 | 按用户分组切分；报告明确指出"不能外推"；给出置信度标签 |
| 群体模型 ≠ 个体规律 | 模型学到的是人群平均关系 | 个人基线特征 + 与个人均值对比的解释模块 |
| 用户过度信任预测 | 30 分钟误差被当成确定结论 | 必给区间与可信度；用户测试专门测量"信任校准" |
| 分布漂移 | 季节、学业/工作周期会改变睡眠 | 记录训练时间；结论限定在训练数据覆盖的时期 |
| 合成数据被误当作结论 | 为跑通流程而生成了合成数据 | 合成数据文件、配置、报告三处都写明"仅用于链路验证" |
| 缺少可选依赖 | 目标机器没有 lightgbm / shap / PyYAML | 代码降级：lightgbm 自动跳过、解释用反事实替代 SHAP、配置用 Python 模块 |
