# 03 数据来源说明

> 本文档说明：**用了什么数据、为什么用它、字段怎么映射、有哪些偏差与限制**。
> 所有结论都对应到代码：数据源定义在 `config/dataset.py`，清洗规则在 `src/data_io.py`，
> 清洗结果（含缺失统计）自动写入 `reports/data_cleaning_report_<数据集>.md`。

---

## 1. 选择数据的四条硬性标准

| 标准 | 要求 | 为什么是硬性标准 |
|---|---|---|
| **可获取与可许可** | 公开可下载，许可允许课程使用（CC0 / CC BY / ODbL 等） | 作业要能复现；不能用需要审批且无法附证据的数据 |
| **字段与预测时点自洽** | 必须同时有"**当天白天的活动量**"与"**当晚睡眠时长**"，且睡眠信息是结果而不是输入 | 本项目预测"就寝前 → 当晚睡眠"，缺任一侧就无法构造监督样本 |
| **样本结构合理** | 同一用户多天记录（能构造滞后/个人基线特征），用户数 ≥ 20 | 只有"每人一行"的横截面数据无法做个人基线，也不能按用户切分 |
| **隐私与伦理可交代** | 已去标识、不包含可识别个人身份的信息 | 睡眠/健康属敏感数据，必须能说明"我没有在未经授权的情况下处理个人数据" |

## 2. 候选数据集的甄别过程

| 候选 | 是否采用 | 判断理由 |
|---|---|---|
| **Fitbit Fitness Tracker Data（Bellabeat / Kaggle, `arashnic/fitbit`）** | ✅ **首选真实数据** | 同时包含日级活动表与睡眠表，可用 `(用户, 日期)` 内连接；30 名用户、约 2 个月，能做滞后与个人基线；页面标注 CC0；被广泛用于教学，结果可比 |

| NSRR（如 SHHS / MESA 等睡眠研究资源） | ❌ | 多为多导睡眠图（PSG）级别的金标准数据，但需要提交研究申请与数据使用协议，课程周期内无法完成，且通常缺少"白天活动 → 当晚时长"的日常配对 |
| Sleep-EDF 等睡眠分期数据集 | ❌ | 标签是**epoch 级睡眠分期**，任务不同（分期 ≠ 时长预测）；样本以少数受试者的整夜信号为主，缺少日级活动信息 |
| 纯加速度计 / 手环原始信号数据集 | ❌ | 缺少可靠的睡眠时长标签，无法构造监督目标 |
| 自建问卷数据 | ❌ | 无法在课程周期内获得伦理审批与足够样本，且自报睡眠时长偏差大 |

> ⚠️ 说明：候选数据集的**样本量、许可与字段**以数据集页面为准；正式提交前请按第 8 节的
> 清单在页面与实际下载的 CSV 上逐条核对一次（本项目已把可核对的字段全部写进配置）。

#### 3.1.1 下载后实测（2026-10-04，本地实际文件）

Kaggle 的压缩包解压后会**多出一层目录**，`config/dataset.py` 里写的是解压后的真实相对路径：

├─ mturkfitbit_export_3.12.16-4.11.16/Fitabase Data 3.12.16-4.11.16/   ← 11 个 CSV，**没有 sleepDay_merged.csv**
└─ mturkfitbit_export_4.12.16-5.12.16/Fitabase Data 4.12.16-5.12.16/   ← 18 个 CSV，**有 sleepDay_merged.csv**

| 4.12–5.12 睡眠表 | 413 条 / **24 名用户** / 2016-04-12 ~ 2016-05-09 |
| 3.12–4.11 活动表 | 457 条 / 35 名用户 / 2016-03-12 ~ 2016-04-09（该段**没有日级睡眠表**） |

| 目标分布 | 均值 **431.9 分钟**（7h12m）、标准差 **100.8 分钟**、范围 123 ~ 796 分钟 |
| 每人天数 | 最少 2 天、中位数 22 天、最多 31 天 |

**两条必须写进报告的判断：**

1. **睡眠表只存在于后一段导出**，所以活动表也必须取同一段，否则 `(user_id, date)` 内连接结果为空。
   这是"先看文件再写配置"的直接收益——如果照页面描述想当然地取 3.12–4.11 那段，流程会跑出 0 条样本。
2. **24 名有睡眠记录的用户里，最终只有 22 名进入建模**：另外 2 名的活动日期与睡眠日期没有交集
   （缺勤日不记录），属正常损耗，不是数据损坏。

#### 3.1.2 一个被数据集限制掉的界面输入

原型的输入页原本包含"你打算几点上床睡觉"。**Fitbit 日表里没有这个字段**，所以：

- 模型的 70 个特征里**不含** `bedtime_minutes`（`models/model_card.json::features` 可核对）；
- 界面改成**检测模型实际使用的特征**：没有这一项就不渲染该输入框，并明确写出
  "当前数据集没有该字段，这一项不会被模型使用"，而不是留一个"填了也不影响结果"的假控件；
- 更关键的是**不能用"当晚实际入睡时刻"来补这个洞**：它是同夜结果，属于泄漏字段
  （`minuteSleep_merged.csv` 里能算出每个夜晚的入睡时刻，但这只能用于事后分析，不能作为预测输入）。

上述 3 条都已在代码中落实，对应文件：`app/app.py`（第 1 页条件渲染）、`src/predict.py`、
`scripts/smoke_test.py`（数据集没有该特征时改测"填了不改变结果"）。

### 3.3 合成数据（默认，仅用于链路验证）

| 项目 | 内容 |
|---|---|
| 生成方式 | `python -m scripts.make_synthetic_data`（`scripts/make_synthetic_data.py`） |
| 输出 | `data/raw/synthetic/daily_records.csv`（交付版工作区里**已删除**该文件，需要时运行上面的命令重新生成） |
| 实测规模 | **1405 条**，30 名用户，2024-01-01 ~ 2024-02-19 |
| 实测分布 | 睡眠时长均值 **416.2 分钟**（约 6h56m），标准差 **56.1 分钟** |
| 内置真实关系 | 就寝越晚越短（≈ -0.42 分钟/分钟）、周末多睡、前一天活动多则略长、个人基础睡眠存在个体差异 |
| 用途 | 在拿到真实数据、或网络不可用时，保证**整条流水线可运行、可验收** |
| 边界声明 | **合成数据上的指标只证明"代码链路正确"，绝不可写进实验结论**；文件头注释、配置文件 `notes`、报告均标注此限制 |

合成数据的一个实现细节值得记录：早期版本用 `(bedtime % 1440) - base_bedtime` 计算
"比平时晚睡多少分钟"，跨零点时会突然差出 1400 多分钟，使生成数据里出现
"越晚睡睡得越久"的反向关系、睡眠时长的离散程度明显失真。改为**环形差值**
（`(x + 720) % 1440 - 720`）后，量纲恢复到合理水平（σ≈56 分钟）。
这类错误说明：**合成数据同样必须做量纲与方向检查**。

## 5. 字段合法性与泄漏控制

### 5.1 判定规则

预测时点定在**就寝前**，因此：

| 字段类别 | 例子 | 是否可用 |
|---|---|---|
| 当天白天的行为 | 步数、中高强度活动、久坐、消耗热量 | ✅ 可用 |
| 用户既往记录 | 前几天/几周的活动与睡眠（滞后、滚动、个人基线） | ✅ 可用（必须 `shift(1)`） |
| 计划与日历 | 计划就寝时刻、星期几、是否周末 | ⚠️ **取决于数据集**：合成数据里有"计划就寝"；Fitbit **日表**没有该字段，但**分钟级睡眠表可以还原实际的入睡/起床时刻**（见 7.5 节），此时界面仍按"模型实际使用的特征"决定是否显示该输入 |
| 当晚的实际睡眠结果 | 卧床时间、入睡时长、睡眠效率、**今晚的**入睡/起床时刻 | ❌ **禁用**（结果字段） |
| **上一晚**的睡眠结果 | 昨晚的入睡/起床时刻、昨晚的睡眠效率与夜醒时长 | ✅ **可用**（属"既往记录"，必须 `shift(1)` 之后才可进入特征） |
| 与结果同源导出的字段 | `TotalTimeInBed`、睡眠片段数 | ❌ **禁用**（属同夜产物） |

### 5.2 代码层面的落实

1. `config/dataset.py` 中 **不把** `TotalTimeInBed` 等字段写进 `column_map`，从源头丢弃；
2. `src/features.py` 所有滞后/滚动特征强制 `groupby(user_id).shift(1)`，即"只用当天之前的信息"；
3. `src/splits.py` 在划分后执行**泄漏自检**：检查 `user_id` 是否跨集合重叠、日期是否跨集合穿透，
   结果写入 `reports/split_summary_*.md`（当前状态：通过）；
4. `src/train.py` 只读取 train/val，`src/evaluate.py` 是**唯一**读取 test 的模块。

## 6. 使用限制与已知偏差（必须在报告中声明）

1. **样本偏差**：Fitbit 数据来自自愿使用手环的志愿者，非随机抽样；
   30 名用户不足以代表任何人群。
2. **设备与算法偏差**：睡眠时长由设备算法估计，不是 PSG 金标准；不同设备的估计口径不同。
3. **时代偏差**：2016 年的数据，作息与设备算法都与当下不同，不能外推到当前年份。
4. **时间跨度短**：约 2 个月，覆盖不到季节变化与长期习惯变化。
5. **缺少关键解释变量**：没有咖啡因/酒精摄入、卧室环境、光照、心理压力、是否有孩子等，
   这些因素在现实中很可能比步数更重要——这也是模型误差的主要来源之一。
6. **无日记信息**：无法区分"睡不着"与"没时间睡"，两类成因的行为含义完全不同。
7. **横截面对照数据集**：`sleep_health_lifestyle` 每人一条，只能用于横向对照，不能做个人基线。
8. **缺失机制**：手环未佩戴的日期会整体缺失（不是随机缺失），清洗报告会给出每日记录数与缺失率。
9. **个体差异远超日间波动（实测）**：22 名用户的个人平均睡眠从 **140 分钟**（`4558609924`）到
   **652 分钟**（`1844505072`），有人个人标准差高达 **384 分钟**（`1644430081`）。
   这几条记录要么反映极端作息，要么反映佩戴/记录口径问题，**标签本身的可信度不足**。
   本项目选择保留并在报告中声明，而不是删掉它们让指标更好看（详见 `reports/error_analysis_notes.md` 第 2 节类型 B）。
10. **用户级样本很少（实测）**：按用户分组切分后，测试集 75 条只来自 **4 名用户**，
    而验证集 4 名用户的平均睡眠（385.4 分钟）比训练集（448.8 分钟）低 63 分钟。
    **换一批测试用户，MAE 可能整体变动 ±10 分钟**，因此报告中的指标不应写到小数位以外。

## 7. 隐私与伦理说明

- 两个真实数据集均为**公开、已去标识**的数据（Fitbit 数据页面标注 CC0）；
- 本项目**不做任何重新识别**（不使用地理位置、不使用用户画像信息），只使用数值化行为字段；
- 用户 ID 在内部仅作为"分组键"使用，报告与图表中不出现原始 ID 全串；

### 7.5.1 为什么会有这一段

Kaggle 下载包里其实有**两个**导出目录，本项目此前只用了后者：

| 目录 | 含 `sleepDay_merged.csv`？ | 此前是否使用 |
|---|---|---|
| `mturkfitbit_export_3.12.16-4.11.16` | **否**（所以一直用不上） | ❌ 未使用 |
| `mturkfitbit_export_4.12.16-5.12.16` | 是（当前标签来源） | ✅ 使用中 |

两段都有 `minuteSleep_merged.csv`（分钟级睡眠：1=asleep / 2=restless / 3=awake），
用它聚合出"每晚睡眠时长"就能把前一段也用起来。**这不是数据增广，是真实的额外样本。**

### 7.5.2 口径规则（都做了实测校验）

| 项目 | 规则 | 实测证据 |
|---|---|---|
| 夜的划分 | `(user, logId)` 段，丢弃 <60 分钟的碎片段，按**起床日**归夜 | 与 `sleepDay` 的日期口径一致 |
| 标签 | 同一夜**各段 asleep 求和**；**优先使用官方 `sleepDay`**，缺失时才用求和值 | 在 410 个共有夜上**完全一致率 96.3%**（若只用"最长段"只有 84.6%，所以必须求和） |
| 活动特征 | **优先 `dailyActivity_merged.csv`**，缺失时用 `hourlySteps` + `hourlyCalories` + `minuteIntensitiesNarrow` 聚合 | 聚合覆盖率 100%（官方日表在 3.12 段只有 42.9%） |
| 活动列等价性 | 五列几乎等价 | `steps` 中位差 0 / 完全一致 81%；`calories` 中位差 2 kcal；三档活动分钟中位差 0、90 分位 0 |
| ⚠️ 已知缺陷 | `sedentary_minutes` 在官方日表里**口径不一致** | 官方 `(三档活动 + 静坐)` 与 1440 的差额在 0 ~ −1438 分钟之间跳动（约一半日子相等），说明同一列混用了"含未佩戴时间"与"仅佩戴时间"两种算法。**这是数据集自身问题，不是合并引入的**，报告中应把它当作活动量的粗指标 |

其他质量事实：`sleepDay_merged.csv` 内部有 3 条重复的 `(用户, 日期)` 行（已在构建脚本中去重）。

### 7.5.3 数据规模变化

| 数据集 | 条数 | 用户 | 特征 | 目标均值 / 标准差 | 日期范围 |
|---|---|---|---|---|---|
| `fitbit_bellabeat`（线上） | 395 | 22 | 70 | 431.9 / 100.8 分钟 | 2016-04-12 ~ 05-12 |
| `fitbit_2seg`（实验） | **799** | **23** | 70 | 436.6 / 105.8 分钟 | 2016-03-12 ~ 05-12 |

特征数**故意保持一致**（70），这样对照实验只改变"数据量"这一个变量。

### 7.5.4 对照结果（同一模型、同一超参数、按用户分组交叉验证）

| 数据集 | 样本/用户 | GroupKFold MAE | 均值基线 | 相对基线提升 | 多种子 MAE 极差 |
|---|---|---|---|---|---|
| `fitbit_bellabeat` | 395 / 22 | **63.8 ± 17.5** | 77.6 | **+17.8%** | 30.8 分钟 |
| `fitbit_2seg` | 799 / 23 | **73.2 ± 7.0** | 81.1 | **+9.7%** | 56.8 分钟 |

**怎么解读：**

1. **稳定性变好**：逐折标准差 17.5 → 7.0 分钟，说明"更多数据让估计更可信"；
2. **精度变差**：MAE 63.8 → 73.2，相对基线提升 17.8% → 9.7%；
3. **原因已定位**（`reports/slice_analysis_fitbit_2seg.md`）：

| 切片 | 条数 | MAE | 偏差 |
|---|---|---|---|
| 4.12 段（标签来自官方日表） | 395 | **65.7** | +18.9 |
| 3.12 段（标签来自分钟级求和） | 404 | **80.5** | +0.8 |
| 活动来自官方日表 | 568 | 66.7 | +16.5 |
| 活动来自聚合补齐 | 231 | **89.2** | −6.9 |

也就是说：**新增的那一段（3.12）本身更难预测**，而且其中用聚合活动特征的行误差最大。
再看用户级误差，最差的用户包括"只有 1 条记录且均值 135 分钟""5 条记录但个人标准差 348 分钟"
这类**记录质量本身不可信**的样本——它们同时放大了切分波动（多种子极差 30.8 → 56.8 分钟）。

### 7.5.5 结论与下一步（写进报告）

1. **不要直接把两段合并当成"加数据就变好"的例子**：本项目的实测恰恰相反，这是诚实且更有价值的结论；
2. 正确用法有三种，按性价比排序：
   - **数据质量门槛**：要求用户至少有 N 天（如 7 天）记录才进入训练集，剔除"1 条记录""个人 σ>5 小时"的样本；
   - **把 3.12 段当作"历史上下文"**：只用它延长滞后/滚动特征的历史，不作为训练与评估样本（需要一个"样本掩码"机制）；
   - **先修活动口径**：`sedentary_minutes` 用统一算法重算后再合并；
   （前两条已在 **第 7.6 节**实现并逐条判定；第三条仍未做。）
3. **这组数字同时给出了"加特征是否有用"的判据**：线上数据集的多种子极差是 30.8 分钟，
   意味着任何小于约 30 分钟的改善都无法与"换一批测试用户"的运气区分——见 `reports/cv_stability_summary.md`
   （该文件现已扩成第 7.6 节 6 个变体的并排表）。

### 7.6 Step 2：质量门槛 + 把 3 月段当"历史上下文"（已实现，含判定）

7.5.5 给出的前两条路线，本节真正做出来并**逐条判定**。两条机制的规则都先验写死在
`config/dataset.py` 里（不是看着结果调出来的），实现放在 `src/features.py::apply_sample_selection`：

| 机制 | 规则 | 期望解决什么 | 配置键 |
|---|---|---|---|
| 质量门槛（`_qg` 变体） | **用户级**整人剔除：记录 < 7 天；或个人睡眠时长标准差 > 300 分钟（5 小时） | 前者让 lag7 / roll7 / 个人基线几乎全是缺失值（模型只能用中位数填）；后者说明"一晚"的定义在这个人身上不成立 | `QUALITY_GATE` → 数据集级 `quality_gate` |
| 历史上下文（`_ctx` 变体） | `2016-04-12` 之前的行**只用于计算**滞后/滚动/个人基线，不作为建模样本 | 4 月开头几天的 `sleep_minutes_lag7` 原本全缺（**131/395 行**），接入 3 月历史后只剩 **18/395 行**缺 | `CONTEXT_ONLY_BEFORE` → 数据集级 `context_only_before` |

⚠️ 顺序很关键：特征必须在**完整历史**上算完，再裁掉行——这样被裁的行仍然能当后面行的历史，
裁剪只改变"哪些行进入建模"，不改变任何一行的特征值。

#### 7.6.1 六个变体的对照（同一模型、同一冻结超参数、同一划分策略）

| 数据集 | 行 / 用户 | 目标 σ | GroupKFold MAE | 均值基线 | 相对提升 | 多种子极差 |
|---|---|---|---|---|---|---|
| `fitbit_bellabeat`（线上） | 395 / 22 | 100.8 | 63.76 ± 17.47 | 77.56 | 17.8% | 30.82 |
| `fitbit_bellabeat_qg` | 376 / 16 | 89.9 | **56.99 ± 10.36** | 72.07 | **20.9%** | **13.61** |
| `fitbit_2seg` | 799 / 23 | 105.8 | 73.23 ± 7.02 | 81.08 | 9.7% | 56.84 |
| `fitbit_2seg_qg` | 780 / 18 | 98.7 | **71.10 ± 4.61** | 77.53 | 8.3% | **7.59** |
| `fitbit_2seg_ctx` | 395 / 22 | 100.8 | **60.67 ± 14.77** | 77.56 | **21.8%** | 25.29 |
| `fitbit_2seg_ctx_qg` | 376 / 16 | 89.9 | **55.00 ± 4.94** | 72.07 | **23.7%** | 14.35 |

#### 7.6.2 判定：用事先量好的噪声底线，而不是"数字变小了"

| # | 对照 | ΔMAE | Δ相对提升 | Δ目标 σ | 相对噪声门槛 | 配对（同一批行的逐 run Δ） |
|---|---|---|---|---|---|---|
| A | `fitbit_bellabeat` → `_qg`（门槛） | −6.77 | +3.1% | −10.9 | 证据不足（门槛 30.82） | —（用户集合不同，不能配对） |
| B | `fitbit_2seg` → `_qg`（门槛） | −2.13 | −1.4% | −7.1 | 证据不足（门槛 56.84） | —（用户集合不同，不能配对） |
| C | `fitbit_bellabeat` → `_ctx`（上下文） | −3.09 | +4.0% | **0.0** | 证据不足（门槛 30.82） | 种子 2/3（−3.90、+1.63、−6.07）；折 4/5 |
| D | `_qg` → `_ctx_qg`（门槛之上再加上下文） | −1.99 | +2.8% | **0.0** | 证据不足（门槛 13.61） | 种子 0/3（+0.16、+2.57、+0.90）；折 1/5 |
| E | `fitbit_bellabeat` → `_ctx_qg`（叠加） | −8.76 | +5.9% | −10.9 | 证据不足（门槛 30.82） | —（用户集合不同，不能配对） |

**配对比较是本节最重要的方法修正**：多种子极差量的是"换一批测试用户"的波动，
对**改变了用户集合**的对照（A/B/E）根本没有意义；而 C/D 两边是**同一批行**
（已核对 `(用户, 日期)` 集合完全一致：395 = 395），同一个随机种子会切出同一批测试用户、
GroupKFold 也会切出同一批折，于是可以逐个 run 算 Δ。
结论是：**C 组方向不一致**（有的 run 变好、有的变差）、**D 组在干净子集上 0/3 种子改善**
——两者都只能写成"证据不足"。

#### 7.6.3 结论（已写进报告）

1. **质量门槛改的不是精度，而是"数据质量声明 + 稳定性"**：22 → 16 名用户、395 → 376 行，
   目标 σ 100.8 → 89.9，MAE 63.76 → 56.99、多种子极差 30.82 → **13.61（−56%）**；
   合并集上更明显（极差 56.84 → **7.59，−87%**）。但用户集合变了，**不能**说"模型对所有人变准了"，
   正确说法是"这批数据里只有 16/22 名用户的记录达到最低可用标准，在这批用户上估计更稳"。
2. **把 3 月段当历史上下文：代价为零、方向为正、量级不够**。一行不删、目标分布不变（Δσ = 0.0），
   平均 −3.09 分钟、逐折 4/5 改善，属于"数据利用方式的修正"（lag7 缺失 131 → 18 行），
   可以保留在**实验分支**（`fitbit_2seg_ctx`）里；但它**没有**超过 30.8 分钟的噪声门槛，
   报告里只能写成"方向性证据"，不能写成"改善"。
3. **两个机制功能重叠**：在门槛之后的干净子集上，上下文反而 0/3 种子改善——
   因为被门槛剔除的用户，正是"最需要历史上下文"的那批人（记录少 → 滞后特征全缺）。
4. **线上配置保持不变**：`ACTIVE_DATASET` 仍是 `fitbit_bellabeat`，不加门槛、不做裁剪。
   理由：(a) 没有任何机制通过噪声门槛；(b) 正式验收指标与 `models/` 必须与部署一致，
   换数据集等于重训重评（会覆盖 `reports/metrics.md`）。
5. 顺带修掉一个**可复现性陷阱**：`user_id` 在"读缓存 clean CSV"时被 pandas 解析成 `int64`、
   在"从原始 CSV 现做"时是 `str`，同一个变体两次运行的类型不同（首次就报了 `KeyError`）。
   现在落盘前统一成 `str`；并用哈希核对过：重跑后 `splits.json` 逐字节一致、70 个特征逐值一致。

### 7.7 Step 2 路线 2：加特征（已实现，含判定）

7.5.5 的第三条路线，也是本轮唯一**不改变线上链路**的改动：新增特征全部挂在
`FEATURES["extra"]` 开关下面，**默认关闭**；只有显式打开的数据集变体才用得上，
所以已部署的模型、手机上的界面、正式指标 `reports/metrics.md` 全都保持不变（依据见 7.7.3）。

#### 7.7.1 加了哪两类特征、为什么是它们

| 新特征 | 列数 | 怎么算 | 为什么值得加 |
|---|---|---|---|
| `history_days` | 1 | 该用户在此行**之前**已有多少天记录（`groupby.cumcount()`，天然只看过去） | 滞后/个人基线在记录开头必然缺失（`lag7` 要等到第 7 天）。"历史够不够"本身是模型该知道的事：刚建档时不该照抄个人基线 |
| 就寝环形历史 | 18 | `bedtime_minutes_sin/cos` 本身 + 它们的 `lag1/2/3/7`（8 列）+ 最近 3/7 天的环形均值 sin/cos（4 列）+ 规律性 `bedtime_regularity_3/7`（2 列）+ 可读的平均就寝时刻 `bedtime_roll*_mean_minutes`（2 列） | ① 就寝时刻跨零点：23:50 与 00:10 只差 20 分钟，直接求平均会得到"相差 1420 分钟"的荒谬结果，必须按 sin/cos 环形算；② "最近一周作息有多规律"（R = 环形合向量长度 ∈ [0,1]）是界面能一句话解释的量 |

两条实现纪律：

1. **原始 `bedtime_minutes` 及其普通滞后不进入建模**（`feature_columns` 显式排除）：
   同一信息已有 sin/cos 表达，留下数值版反而会带来"0 点处的人为断层"；
2. 环形滚动一律先 `groupby(用户).shift(1)`、再 `transform(rolling)`，**窗口不跨用户**
   （对照组：基准里同名的滚动特征恰恰有这个缺陷，见 7.7.4 末段）。

#### 7.7.2 三个新变体（与基准是同一批行 → 可以做配对比较）

| # | 对照 | 新增列 | 设计意图 |
|---|---|---|---|
| F | `fitbit_bellabeat` → `fitbit_bellabeat_f2` | +1（`history_days`） | 该数据集**没有**就寝时刻字段，这是纯 `history_days` 的对照 |
| G | `fitbit_2seg` → `fitbit_2seg_f2` | +19 | 在 799 行的合并集上试"就寝环形历史 + `history_days`" |
| H | `fitbit_2seg_ctx_qg` → `fitbit_2seg_ctx_qg_f2` | +19 | 在候选配置（历史上下文 + 质量门槛）之上再加特征 —— 本步最终候选 |

`fitbit_2seg` 当初为了隔离"数据量"这一个变量，把 `bedtime_minutes` 从配置里丢掉了；
新变体用 `_derive(..., undrop_columns=["bedtime_minutes"])` 显式把它放回来，
而不是另抄一份文件配置（抄一份就会引入看不见的差异）。

#### 7.7.3 “零风险”是有哈希依据的

| 检查 | 实测结果 |

| 特征列变化 | F +1 / G +19 / H +19，**移除 0 列**（由两次评估的 `feature_list` 差集算出，见 `reports/gate_experiment.md` 第 1.1 节） |

| 线上产物 | `models/*`（含 `model.pkl`、`model_card.json`、`quantiles.pkl`）与 `reports/metrics.md` **哈希不变** |
| 新增文件 | 只有 `data/processed/*_f2_{clean,features,splits}.*` |
| 默认关的直接证据 | `features_cfg()["extra"]["enabled"] == False`；`feature_columns()` 返回的 70 列与改动前逐值一致 |

#### 7.7.4 结果与判定：加特征这条路**同样没有超过噪声门槛**

| # | 对照 | 基准 MAE | 变体 MAE | ΔMAE | 多种子极差 | 配对：逐种子 Δ / 逐折 Δ |
|---|---|---|---|---|---|---|
| F | `fitbit_bellabeat` → `_f2` | 63.76 | 63.77 | **+0.01** | 30.82 → 30.77 | 1/3 改善（+0.03、+0.08、−0.14）；3/5（+0.43、−0.08、+0.12、−0.29、−0.12） |
| G | `fitbit_2seg` → `_f2` | 73.23 | 75.26 | **+2.03** | 56.84 → 71.45 | 2/3（**+12.83**、−2.34、−1.78）；3/5（+6.10、+11.15、−0.94、−4.39、−1.73） |
| H | `_ctx_qg` → `_ctx_qg_f2` | 55.00 | 54.24 | **−0.76** | 14.35 → 19.70 | 2/3（−1.30、−2.17、**+4.05**）；4/5（−0.20、−1.52、−2.06、−0.42、+0.36） |

怎么读这三行（**不能只看 ΔMAE 的正负号**）：

1. **F 是零结果**：单独加 `history_days`，平均差异 0.01 分钟，等于没有。
   可能的原因是 22 人 / 395 行下"历史长度"与其它列高度相关、增量信息被稀释；
   但这只是解释，不是证据，报告里只写"零结果"。
2. **G 在合并集上不但没改善，平均还差 2 分钟**，且有一个种子退化 12.83 分钟。
   就寝时刻由 `minuteSleep` 聚合而来，两段导出之间的口径差异（见 7.5.2）可能把噪声带进特征；
   这再次说明"特征更多 ≠ 更准"。
3. **H 是本轮唯一还值得继续看的候选**：平均 −0.76 分钟、逐折 4/5 改善，
   但逐种子最大的改善被另一个种子的 **+4.05** 抵消（三种子平均 +0.19），
   且多种子极差从 14.35 涨到 19.70 —— 按事先定好的规则只能写成
   **"证据不足 / 方向不一致"**，不能写成"改善"。
4. 因此**线上配置保持不变**（`ACTIVE_DATASET=fitbit_bellabeat`、`extra.enabled=False`）。
   要把它变成结论，需要更多用户或更长的记录，而不是继续在同一批 22 人身上挑数字。

**顺带发现的实现缺陷（只登记、本轮未修）**：`src/features.py::add_rolling_features` 是
"先按用户 `shift(1)`、再对**整张表** `rolling(w)`"，窗口会越过用户边界 ——
每个用户**前 w−1 行**的 `*_roll{w}_*` 混进了上一个用户的数值（因为设了 `min_periods`，
它不会变成缺失值，而是安静地算出一个"别人的平均值"）。实测（`fitbit_2seg`，799 行）：

| 列 | 与"分组内计算"不一致的行 | 其中"本该缺失却算出了值" | 两边都非空时的最大差 / 平均差 |
|---|---|---|---|
| `steps_roll7_mean` | 120 / 799 | 43 | 6673 步 / 195 步 |
| `sleep_minutes_roll7_mean` | 120 / 799 | 43 | 203.3 分钟 / 4.8 分钟 |
| `sedentary_minutes_roll3_mean` | 41 / 799 | 41 | （两边都非空时差为 0） |

为什么**不趁这次一起修**：修它等于改变**基准特征值**，会让已上线的 `models/model.pkl`
与正式指标 `reports/metrics.md` 立刻失效（必须重训 + 重新验收），而本轮的目标是"零风险加特征"。
修法只有一行——把 `shifted.rolling(...)` 换成
`g[col].transform(lambda s: s.shift(1).rolling(...))`（新增的环形特征用的就是这种写法）——
建议作为**独立一轮**做，做完必须重跑 `src.train` / `src.evaluate` / 本节的对照表。

#### 7.8.4 结果（全部实测，可复现）

- **特征 7 个**：`age`、`active_minutes`、`stress_level`、`heart_rate_mean`、`steps` +
  **`gender_Female` / `gender_Male`**；划分 random：train 226 / val 74 / test 74。
- **模型**：gradient_boosting(300, lr=0.1, depth=3)，测试集 **MAE 3.56 分钟、R²=0.989**
  （均值基线 43.6 分钟）。
  ⚠️ **这个数字不能与线上 fitbit_bellabeat（MAE 41.9 分钟）比大小**：本数据集字段之间
  近乎确定性相关（规则生成的数据），低误差是数据生成机制的结果，不是"模型更强"。
  训练时验证集 80% 区间的实际覆盖率只有 64.9%，也印证了这里的"高分"不能过度解读。
- **性别差异（374 人）**：女性 433.8 分钟 vs 男性 422.2 分钟，Welch **p=0.019 显著**；
  睡眠质量（7.66 vs 6.97）、压力（4.68 vs 6.08）、心率（69.3 vs 71.1）也显著；
  步数（p=0.78）与活动量（p=0.98）**不显著**。
- **年龄混杂必须控制**：两组年龄差 10.3 岁（47.4 vs 37.1，p<0.0001）。回归系数会**翻转**：
  只看性别 **−11.6 分钟**(p=0.0187) → 加年龄 **+12.4 分钟**(p=0.0314) →
  再加压力/步数/心率/活动量 **+28.7 分钟**(p<0.0001)；R² = 0.015 → 0.130 → 0.747，
  其中**压力自评 −23.9 分钟/分**（p<0.0001）是最重的一项。
  分层也一致：<35 岁层里男性反而多睡 +26.3 分钟，说明整体那个"女性睡得更久"
  主要来自两组的**年龄结构**。
- **消融实验（同一超参、同一批 train+val、同一测试集）**：去掉两个性别哑变量后
  MAE 3.6 → **3.5** 分钟、R² 都是 0.989；只用性别 R² 仅 **0.035**；
  特征重要性里 `gender_Female` 排第 **6/7** 位。
- **结论（写进报告的版本）**：性别值得纳入**分析口径与误差切片**（否则会得出
  "女性睡得更久"这类被年龄混杂的结论），但**不值得指望它提升预测精度**；
  这是"相关"而非"因果"。
- 完整表格与图：`reports/sleep_health_lifestyle/gender_analysis.md`、`figures/fig_gender_sleep.png`。

## 7.8.8 第五轮复核（2026-10-09：把「填了没反应」讲清楚）

> **这一轮不改模型、不改数据、不改线上报告**：只加"把预测讲清楚"的两件事
> （① 输入灵敏度实测、② 两段式归因），外加一次注释里**悬空引用**的修正（见第 5 节）。
> 手环线的点预测、区间、典型误差与第四轮完全一致（488.8 分钟 / [374.5, 536.2] / ±1.5 小时），
> 说明这是**纯加法**。

### 1. 触发（真实问题，不是设想）

主试自测时报过一个现象：**手环线怎么改输入、预测都差不多**，看起来"填了没反应"。
这条线用的是 Fitbit 真实数据：70 个特征里绝大多数是**该用户自己的历史**（滞后 / 滚动 / 个人基线），
今天填的三个活动量只是微调——所以"看起来没反应"是**模型的真实性质**，但界面上原本没有任何
数字说明这一点，用户只能猜。第二数据集接进界面后（§7.8.7），"这一项到底有没有用"的疑问只会更多。

### 2. 做了什么（两处代码 + 一处配置）

| 位置 | 函数 / 字段 | 作用 |
|---|---|---|
| `src/predict.py` | `typical_error_hours(card)` | 从模型卡取验证集典型误差（手环线 **±1.5 小时**、横截面线 **±0.1 小时**），供"逐项影响 vs 模型自身误差"对比——这是"为什么几十（分钟）的差别看不出来"的直接依据 |
| `src/predict.py` | `field_sensitivity(...)` | 把**每一项单独拉到自己的两端**（数值项各 5 个点、单选项用全部选项；其余项保持用户填的值）组成**一次批量 `model.predict`**，取 max−min 作为该项的实测影响；`supported=False` 表示"模型根本没用到这一项"（横截面线没有这种项；手环线若换成不含该字段的数据集才会出现） |
| `src/predict.py` | `split_baseline(...)` | 把点预测拆成**基线 + 今日调整**：手环线基线＝该示例用户最近 28 天的中位数（`history_median`）；横截面线没有个人历史，基线＝训练数据中位数（`stats_median`，`n_days=0`）。两种口径都在界面文案里写明，避免把"人群典型值"说成"你的基线" |
| `app/app.py` | `sensitivity_values` / `cached_sensitivity` / `sensitivity_lines` / `sensitivity_summary` | 挑扫描点；按"数据集 + 输入签名"缓存在 `st.session_state`（表单没提交的值不算数）；渲染逐项清单（影响很小的项加后缀说明）与总结句 |
| `config/dataset.py` + `src/evaluate.py` | `DATASETS["sleep_health_lifestyle"]["report_notes"]` | 第二数据集的"口径提醒"**先验**（低 MAE 是数据生成机制的假象、只能读成人群中心值、性别是分析变量），由 `src/evaluate.py` 原样写进 `reports/sleep_health_lifestyle/metrics.md`——手写进报告会在下次重跑时丢失 |

### 3. 实测数字（2026-10-09，AppTest 真实渲染 + 脚本复算）

手环线（示例用户 2026352035 的 28 天历史；默认输入 7,000 步 / 25 分钟中高强度 / 600 分钟久坐）：

| 项目 | 实测值 |
|---|---|
| 点预测 / 区间 / 典型误差 | **488.8 分钟（8 小时 09 分）** / [374.5, 536.2] / **±1.5 小时** |
| 两段式 | 个人基线 **520.5 分钟（8 小时 40 分）** ＋ 今日调整 **−31.8 分钟** = 488.8；基线用的中位数：步数 5,260 / 中高强度 0 / 久坐 658 分钟（n=28） |
| 逐项实测影响 | **步数 56 分钟**（8h01~8h57）、**久坐 69 分钟**（6h59~8h08）、**中高强度 6 分钟**（8h08~8h14） |
| 边界如实写明 | 步数超过约 20,000 步后预测不再变化（树模型不外推），填到上限时界面提示 |

横截面线（默认输入：男 / 43 岁 / 压力 5 / 心率 70 / 活动 60 分钟 / 7,000 步）：

| 项目 | 实测值 |
|---|---|
| 点预测 / 典型误差 | **435.8 分钟（7 小时 16 分）** / **±0.1 小时** |
| 两段式 | 人群典型值 **435.8 分钟（7 小时 16 分）** ＋ 调整 **0.0 分钟**；界面同时写明"这条线不存在**你的**基线" |
| 逐项实测影响 | **压力自评 94**、**活动分钟 61**、**年龄 20**、**心率 17**、**步数 17**、**性别 3** 分钟 |

两个结论照实写：

1. **几十（分钟）量级是真的**：手环线逐项影响的量级（6~69 分钟）小于模型自己的典型误差（±1.5 小时），
   所以"点估计看不出变化"不是 bug；界面因此明写"**上面那个区间更值得看**"。
2. **灵敏度是"点完才算"**：界面是表单，`cached_sensitivity` 只在提交后重算，文案统一写成
   "点「生成预测」后……实测给你看"，**不写"实时"**（不实承诺已登记为 `docs/04` 第 29 条）。

性能（同一次运行内计时）：15 个候选值**一次批量**预测 **52–54 ms**；一次 `predict_one`（含两段式）**124 ms**。
对比：改批量之前按候选值**逐行**调用 `model.predict` 时 15 次约 **1.2 s**（单行 sklearn 调用固定开销约 80 ms），
结果页每次提交都会明显卡一下——已登记为 `docs/04` 第 28 条。

### 7.8.9 第六轮复核（2026-10-10）：手环线预测的**确定性**（同输入三次完全相同）

### 7.8.10 第七轮复核（2026-10-10）：默认进入人群线 + 手环线灵敏度按**真实作息**更正

**为什么查**：演示时再次被质疑"手环用户的预测老在 8:00–8:10 附近"。`§7.8.9` 给出的反驳

本轮把"填一整天"改成**真实作息联动**（活动多 → 久坐少）重测，并据此改了默认人群线与输入页提示。

**实测**（复刻界面取点链路；基线＝示例用户自己的习惯 **7,000 步 / 中高强度 25 分 / 久坐 600 分 = 488.8 分钟（8h09）**）

| 填法（按真实作息） | 预测 | 相对基线 |

| 久坐 600 → 900 分（其余不变） | 419.2 分钟 | −69.6 分钟 |
| **示例用户自己的习惯（＝基线）** | **488.8 分钟（8h09）** | 0 |
| 很活跃的一天：15,000 步 + 久坐 300 分 | 479.7 分钟 | **−9.1 分钟** |
| 只把步数降到 1,500（久坐不动） | 537.7 分钟 | **+48.9 分钟** |

**结论**

1. **"更活跃"这一侧几乎不动**：从"他自己的习惯"往上走最多只有 **9 分钟**；往下（更闲）才有 **−77 分钟**

2. **两个方向互相抵消**：模型学到「步数↑→睡眠↓」「久坐↑→睡眠↓」，而真实的一天里这两项必然反向变动，
