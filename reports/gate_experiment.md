读法：

1. **ΔMAE < 0** 表示变体更准；但只有 `|ΔMAE| > 多种子极差` 才算“超过噪声门槛”，
   否则无法与“换一批测试用户”的运气区分开；
2. **Δ目标标准差** 是任务难度的变化：门槛剔掉高波动用户后标准差必然下降，
   此时 MAE 下降是**天经地义**的，所以必须同时看 Δ相对提升是否变好；
3. **配对** 这一列只在两个数据集是**同一批行**时才有值（见 4.1），它是本表里最严格的证据；
4. 两边行数不同时（A/B/E 组），组间 MAE 的绝对差也会被“用户构成”影响，
   要结合 `reports/sample_selection_*.md` 的剔除名单一起读。

### 4.1 配对比较（同一批行 / 同一批测试用户）

**为什么需要**：多种子极差量的是“换一批测试用户”的波动，它天生判不了
“改变了用户集合”的对照（质量门槛把一些用户整个删掉了，两边根本不是同一批测试用户）。
但如果两个数据集是同一批行，那么同一个随机种子会切出**同一批测试用户**、
GroupKFold 也会切出**同一批折**，于是可以逐个 run 配对
`Δ_run = MAE_变体 − MAE_基准`，把“换用户/换折”的方差消掉。

| 对照 | 逐种子 ΔMAE（20% 测试集） | 种子改善数 | 逐折 ΔMAE（GroupKFold） | 折改善数 | 范围一致（种子 / 折） |
|---|---|---|---|---|---|
| A `fitbit_bellabeat` → `fitbit_bellabeat_qg` | —（用户集合不同，不能配对） | — | — | — | — |
| B `fitbit_2seg` → `fitbit_2seg_qg` | —（用户集合不同，不能配对） | — | — | — | — |
| C `fitbit_bellabeat` → `fitbit_2seg_ctx` | -3.90、+1.63、-6.07 | 2/3 | -4.94、-3.23、+1.12、-7.59、-0.80 | 4/5 | ✓ / ✓ |
| D `fitbit_bellabeat_qg` → `fitbit_2seg_ctx_qg` | +0.16、+2.57、+0.90 | 0/3 | +0.01、+0.01、+1.03、+1.52、-12.51 | 1/5 | ✓ / ✓ |
| E `fitbit_bellabeat` → `fitbit_2seg_ctx_qg` | —（用户集合不同，不能配对） | — | — | — | — |
| F `fitbit_bellabeat` → `fitbit_bellabeat_f2` | +0.03、+0.08、-0.14 | 1/3 | +0.43、-0.08、+0.12、-0.29、-0.12 | 3/5 | ✓ / ✓ |
| G `fitbit_2seg` → `fitbit_2seg_f2` | +12.83、-2.34、-1.78 | 2/3 | +6.10、+11.15、-0.94、-4.39、-1.73 | 3/5 | ✓ / ✓ |

若两种协议的**每一个 run 都改善**，那才说明改善来自特征本身，
而不是“这次运气好、抽到的测试用户/折更容易”；只要出现变好的 run 与变差的 run 混在一起，
就应该老实写成“方向不一致 → 证据不足”。
（“范围一致”列表示两侧的训练/测试范围确实完全相同，配对才有意义。）

## 6. 结论

- 没有任何对照的 ΔMAE 超过基准数据集的“多种子极差”；对**改变了用户集合**的对照（质量门槛）这条门槛本来也不适用（见下）。
- 在**同一批行的配对比较**里，没有任何对照做到“逐种子、逐折都改善”：有的 run 变好、有的 run 变差，改善量级只有几分钟的零头。
- 三类对照的性质完全不同，报告里必须分开写：
  - **只改“哪些行进入建模”**（质量门槛 A/B 与叠加的 E）：它同时改变了目标方差与基线 MAE，
    所以既不能用“换一批用户的噪声”来判定，也不能说“模型对所有人变准了”；
    正确读法是**数据质量声明**——“这批数据里只有 N 名用户的记录达到最低可用标准”，
    证据是“在这些用户上逐折标准差与多种子极差同时变小”；
  - **一行都不改、只改特征看到的历史**（历史上下文 C/D，Δ目标标准差 = 0.0）：
    同一批行、同一批测试用户、同样的目标分布，是严格的可控对照，
    差异可以直接归因到特征，但**方向是否稳定**还要看下面这几行；
  - **只改“有哪些特征列”**（加特征 F/G/H，Δ目标标准差 = 0.0）：
    同样是严格的可控对照，区别在于它新增的是**列**而不是历史长度；
    这也是唯一一种“如果真有效，可以把界面上的输入表单做小一点”的改动
    （例如用历史规律性替代让用户手填每一项活动）。
- **C** 历史上下文：同一批行，滞后/滚动/基线改用更长的历史：配对 → 逐种子 2/3 改善（均值 -2.78 分钟），逐折 4/5 改善（均值 -3.09 分钟）；**方向不一致 → 判为证据不足**。
- **D** 历史上下文（在质量门槛之上再加）：配对 → 逐种子 0/3 改善（均值 +1.21 分钟），逐折 1/5 改善（均值 -1.99 分钟）；**方向不一致 → 判为证据不足**。
- **F** 加特征：同一批行，新增 history_days（该数据集没有就寝时刻字段）：配对 → 逐种子 1/3 改善（均值 -0.01 分钟），逐折 3/5 改善（均值 +0.01 分钟）；**方向不一致 → 判为证据不足**。
- **G** 加特征：同一批行，新增就寝环形历史 + history_days：配对 → 逐种子 2/3 改善（均值 +2.90 分钟），逐折 3/5 改善（均值 +2.04 分钟）；**方向不一致 → 判为证据不足**。
- **H** 加特征（在候选配置之上再加一轮）：配对 → 逐种子 2/3 改善（均值 +0.19 分钟），逐折 4/5 改善（均值 -0.77 分钟）；**方向不一致 → 判为证据不足**。
- 这一步的价值不只在结论，还在**过程可复核**：门槛是先验写死进配置的、
  对照是并排跑的、判定用的是一条事先量好的噪声底线，而不是“数字看起来变小了”；
- 所有变体的特征表、划分与专属报告都保留（`reports/sample_selection_*.md`、
  `reports/cv_stability_*.md`），可以用 `--skip-prepare` 复算同一张表。

## 8. 本轮**没有**纳入的候选与已知缺陷

这一节的作用是让“没做”也可复核：既不假装做过，也不让读者以为已经做过。

### 8.1 想加、但本轮没加的特征

| 候选 | 为什么本轮没做 | 下一步怎么补 |
|---|---|---|
| 晚间活动窗口（例如 18:00 之后的步数/活动量） | 现有活动列是**全天汇总**，没有分钟级活动表；本机有的分钟级导出只有 `minuteSleep`（睡眠），造不出“晚间活动” | 需要 minuteSteps / minuteCalories 这类导出；拿不到就只能在报告里写成“无法验证的假设” |
| 前几晚的睡眠碎片与效率（`sleep_in_bed_minutes`、`sleep_awake_minutes`、`sleep_restless_minutes`，滞后一天使用是合法的） | 数据已备在 `data/interim/fitbit_2seg/daily.csv`，但 `data_io` 只保留规范列，要先加进 `src/config.py::OPTIONAL_NUMERIC`——那会改动**所有**数据集已落盘的中间表 | 单独一轮：加规范列 → 全量重建 → 重跑本脚本对照（约 1 小时，风险中等；本期为了“零风险”暂不做） |
| 活动口径修复（两段导出的 `sedentary_minutes` 算法不一致） | 这是**数据口径**问题而不是特征问题，改完必须重建 `fitbit_2seg` 及全部变体 | 见 `scripts/build_fitbit_2seg.py` 生成的口径报告 |

### 8.2 本轮发现的实现缺陷（**只登记，未修**）

`src/features.py::add_rolling_features` 用的是“先按用户 shift、再全局 rolling”：
`shifted = g[col].shift(1)` 之后紧跟 `shifted.rolling(w)` —— 这个 rolling 作用在**整张表**上，
窗口会越过用户边界，于是每个用户**前 w−1 行**的 `*_roll{w}_*` 里混进了上一个用户的值；
因为设了 `min_periods`，它不会变成缺失值，而是安静地算出一个“别人的平均值”。

为什么本轮不修：修它等于改变**基准特征值**，会让已上线的 `models/model.pkl` 与正式指标
`reports/metrics.md` 立刻失效（必须重训 + 重新验收），而本轮的目标是“零风险加特征”。

- 修法：把 `.rolling(...)` 改成 `g[col].transform(lambda s: s.shift(1).rolling(w).mean())`（本轮新增的就寝环形特征用的就是这种写法）；
- 影响面：每个用户的前 w−1 行 × 全部滚动列（`roll3`/`roll7` × `mean`/`std` × 9 个基础列）；
- 定性：按用户分组交叉验证时，测试用户的这些行同样受影响，所以这是“该修的错”，不是“可以忽略的近似”；
- 复现与量化见 `docs/data_source.md` 第 7.7.4 节与 `docs/ai_usage.md` 的踩坑记录。
