# 用户测试任务脚本 / User Test Tasks

> 目的：检验交互原型是否能让普通用户看懂结果、判断可信度、知道影响因素。
> 至少 3 名参与者（作业第 5 条要求）、建议 5 名（同学/朋友即可），每人 5–8 分钟，全程不提示、不解释，
> 只在参与者完全卡住时记录"卡住"并给出最小提示。

---

## 0. 测试前准备（主试执行）

> 完整的主试操作说明（三种分发方式、局域网共享、如实说明话术、常见问题）见 `user_test/host_guide.md`；
> 纸笔记录用 `user_test/record_sheet.md`（每位参与者一页，字段与 `raw.csv` 一一对应）；
> 要在 QQ 群 / 微信里找同学（含远程自助）直接用 `user_test/qq_invite.md` 里可复制的招募文案与发布纪律。

```cmd
:: 1) 确认模型已训练、界面能启动（一个命令：检查环境 + 打印局域网地址 + 启动）
python -m scripts.run_app
::    Windows 下可直接双击项目根目录的 run_app.cmd

:: 2) 改过代码时先自检
python -m scripts.smoke_test
python -m scripts.test_app
```

- 准备一台电脑、一个浏览器窗口（建议 100% 缩放，窗口最大化）；
- 关闭聊天工具通知，避免打断计时；
- 准备 `user_test/raw.csv` 用于记录（已有 4 名参与者 P1–P4 的记录，见 `user_test/summary.md` 与 `user_test/questionnaire.md`）；
- 征得参与者口头同意：这是课程作业原型，不是医疗器械，记录是匿名的。

> ⚠️ 测试时必须如实说明的已知限制：原型载入的历史是演示用户 `2026352035` 的 28 天记录
> （2016-04-12 ~ 2016-05-12，见 `models/history_sample.csv`），参与者填的只是"今天的活动"，
> 会拼在这段历史之后参与计算。因此本轮测试检验的是界面能否把结果与不确定性说清楚，
> 而不是"对参与者本人预测得准不准"。建议照读：
> "这个原型现在用的是示例用户的历史记录，你填的是今天的活动；所以请你重点看它说的东西对不对得上你的理解，
> 先不用管数字准不准。"（这句不透露任务答案，因此不算引导，可写进测试记录。）

---

## 1. 开场白（照读，避免引导）

> "这是一个预测今晚睡眠时长的小工具，我需要你看它能不能把话说清楚。
> 请你像平时一样使用它，过程中如果有不理解的地方可以直接说。
> 我不会提示你怎么操作，也不会判断你答得对不对。"

必须避免的说法（会污染测试结果）：
- ❌ "你看这里有个区间，意思是……"
- ❌ "点这个按钮就能看到解释"
- ❌ "这个预测大概会误差半小时"

---

## 2. 任务清单

### 任务 T1：得到一次预测（记录完成率与用时）

> "假设现在是晚上 22:30，你今天走了 4,000 步、做了 10 分钟比较累的运动、坐了 10 个小时，
> 打算 00:30 睡。请用这个工具告诉我：今晚大概能睡多久？"
>
> 主试注意：当前数据集（Fitbit 日表）没有"就寝时刻"字段，界面不会出现时间输入框——
> 这是刻意设计的（避免"填了也没用"的假控件）。照读题目即可，
> 若参与者问"怎么没有填睡觉时间的地方"，如实回答"这个工具现在不用这一项"，并把这个提问记录下来（它是很有价值的测试发现）。
> 若换成含该字段的数据集，这句话就对应到"你打算几点上床睡觉"输入。

- 是否完成：记录方式＝完成 / 部分完成 / 失败（失败时记录卡在哪一步）
- 用时：记录方式＝从"开始"到说出结论的秒数
- 是否需要提示：记录方式＝无提示 / 1 次 / 多次
- 操作错误：记录方式＝误点、回退、填错字段等（记录次数与内容）

### 任务 T2：正确复述不确定性与可信度

> "这个结果有多可靠？请你用自己的话说一下，这个数字能不能当成一定会发生的事。"

- 是否提到"是一个范围/区间"：说明＝是 / 否
- 是否提到"不一定/是估计"：说明＝是 / 否
- 是否把预测当成确定事实：说明＝是 / 否（这是关键风险点）
- 原话摘录：说明＝逐字记录，便于后续分析

### 任务 T3：指出主要影响因素

> "为什么是这个结果？请你指出影响最大的因素，并说说它让预测变长还是变短。"

- 是否找到解释页：说明＝是 / 否（用时）
- 是否说出主要因素名称：说明＝是 / 否
- 是否说对"变长/变短"的方向：说明＝正确 / 错误 / 说不清
- 是否把解释当成因果（如"所以我只要 22:30 睡就一定能睡 8 小时"）：说明＝是 / 否

### 任务 T4：说出一个可行动的改变（可选）

> "如果你想让今晚的预测变长一些，你会做什么？（不需要真的去做）"

- 是否给出与解释一致的行动：说明＝是 / 否
- 是否出现夸大或医疗化表述：说明＝是 / 否

### 任务 T5：主观评价（1–5 分）

> "请给下面几项打分，1 分=非常不同意，5 分=非常同意。"

1. 我能看懂结果在说什么；
2. 我知道这个预测有多可靠；
3. 我明白哪些因素影响了结果；
4. 界面上没有让我焦虑或被评判的措辞；
5. 我愿意在现实中偶尔用它看看。

并追问两个开放问题：
- "哪一步最费劲？为什么？"
- "如果只能改一个地方，你会改什么？"

> ⚠️ 远程群发版的口径差异：为了口语化，`user_test/qq_invite.md` 第 3 节把第 2 项写成
> "觉得估得挺准"、第 5 项写成"我愿意用它"。第 5 项只是换了说法；第 2 项语义变了
> （主观准确度 ≠ 信任校准）。汇总时：① 第 2 项的分不参与通过线判定（原型用的是示例用户
> 的历史数据，分数必然偏低）；② "信任校准"一律用开放回答"能不能当成一定会发生的事"判定。

## 3. 记录表字段（写入 `user_test/raw.csv`）

- `participant`：含义＝匿名编号，如 P1（不要写真实姓名）
- `date`：含义＝测试日期
- `age_group` / `gender`：含义＝可选，仅用于分组，不记录可识别信息
- `device_user`：含义＝平时是否使用手环（是/否）——影响先验经验
- `t1_completed` / `t1_seconds` / `t1_hints`：含义＝任务 1 完成情况
- `t2_mentions_range` / `t2_mentions_uncertain` / `t2_treats_as_fact`：含义＝任务 2 关键判断
- `t3_found_explain` / `t3_top_factor` / `t3_direction_correct` / `t3_causal_misread`：含义＝任务 3 关键判断
- `t4_action`：含义＝任务 4 的答案（简述）
- `q1_understand` … `q5_willing`：含义＝主观评分 1–5，分别对应"能看懂 / 觉得估得挺准 / 影响因素合理 / 没有焦虑措辞 / 愿意用"（远程口语版；原设计第 2 项为"知道有多可靠"，两者语义不同，见第 2 节 T5 的提醒）
- `q9_too_few`：含义＝问卷额外加的反向题"功能太少太单调"（1–5，越高越不满意）。本轮实际用的是 `user_test/questionnaire.md` 那份 9 题问卷，题目原文与字段对照都在那里；该题只作参考，不进通过线
- `hardest_step` / `one_change`：含义＝两个开放问题原话（尽量逐字，不要概括）
- `notes`：含义＝其他观察（犹豫、皱眉、误操作等）

## 4. 通过线（与 `docs/01_requirements_analysis.md` 第 7.2 节一致）

- T1 完成率：通过线＝≥ 80%（5 人中 ≥ 4 人）
- T1 用时中位数：通过线＝≤ 60 秒
- T2 提到"范围/不一定"：通过线＝≥ 4/5 人
- T2 把预测当确定事实：通过线＝0 人
- T3 指出主要因素：通过线＝≥ 3/5 人
- T3 因果误读：通过线＝≤ 1 人（出现即需改文案）
- Q1 平均分：通过线＝≥ 4.0
- Q4 出现"焦虑/被评判"：通过线＝0 人

> 人数口径：作业第 5 条要求"至少 3 名同学"，本表按 5 人写是为了统计更稳、也更接近
> `docs/01` 第 7.2 节的原始口径。若最终只收到 3 人，就按同一比例换算，不要硬凑 4/5：
>
> - T1 完成率：5 人口径＝≥ 80%；3 人时等价要求＝≥ 80% → 3 人全中
> - T2 提到"范围/不一定"：5 人口径＝≥ 4/5（80%）；3 人时等价要求＝3 人全中
> - T3 指出主要因素：5 人口径＝≥ 3/5（60%）；3 人时等价要求＝≥ 2 人
> - T1 用时中位数 / T2 当事实 0 人 / T3 因果误读 ≤1 人 / Q1≥4.0 / Q4 0 人：5 人口径＝不变；3 人时等价要求＝不变

>
> 并在 `user_test/summary.md` 第 1 节的"实测"列写成 `2/3` 这种分数形式，把分母写清楚。

## 5. 测试后必做

1. 当天把 `raw.csv` 补齐（不要事后凭记忆补）；
2. 把"原话"尽量逐字记录——它比评分更有价值；
3. 用 `user_test/summary.md` 汇总，并写出至少 3 条改进建议，
   每条都要标注归因：属于模型/数据问题，还是界面/文案问题，并给出优先级与预估工作量。
